# Requirements

What we will actually build, stated concretely. Derived from `assignment.md` during
the planning session of 2026-09-11/12.

**`assignment.md` remains authoritative.** This file resolves it into testable
behaviour; where the two ever disagree, the assignment wins and this file is wrong.
Technical choices live in `docs/decisions.md`; sequencing lives in `docs/plan.md`.

Each section notes the assignment requirement it serves.

---

## 1. Roles and permissions — *assignment #3*

Three levels of access.

| Capability | Anonymous | User | Admin |
|---|:---:|:---:|:---:|
| Register, log in | ✅ | — | — |
| View the list of rooms | — | ✅ | ✅ |
| View any room's schedule | — | ✅ | ✅ |
| Book a free slot | — | ✅ | ✅ |
| View own bookings | — | ✅ | ✅ |
| Create, edit, delete rooms | — | — | ✅ |
| View all bookings across users | — | — | ✅ |

- Registration is email + password. Every self-registered account gets the `User` role.
- One `Admin` account is seeded from configuration; there is no promote-to-admin flow.
- Unauthenticated access to anything beyond register/login returns 401; authenticated
  access to an admin-only endpoint returns 403.

## 2. Rooms — *assignment #4*

- A room has a **name** and a **capacity**. Nothing else.
- Admins create, edit and delete rooms. Deleting a room removes its slots.
- Every authenticated user can list rooms.

## 3. Slots — *assignment #4*

- A slot is a fixed, bookable window on exactly one room. Slots are **rows**, not a
  concept computed at read time.
- **The grid is global and identical for every room:** 08:00–18:00 Europe/Kyiv,
  60-minute slots, ten slots per room per day. There is no per-room schedule and no
  custom slot length. The hours are wall-clock times in the display zone of §7, so a
  slot's UTC instant shifts by an hour across a daylight-saving boundary while its
  local hour does not.
- **Horizon: 14 days forward** from the point of seeding. The seeding window is a
  single constant — widen it if the review window slips.
- Slots are **generated by the server**. Clients never supply a time; creating a room
  generates that room's slots for the remaining window.
- A slot is either free or booked. There is no third state.

## 4. Booking — *assignment #5*

- A user books **exactly one slot per request**, identified by its server-generated
  `slotId`. The client never sends a time.
- A slot can be booked by **at most one user, ever**.
- **Bookings cannot be cancelled, rescheduled or modified.** This is a deliberate
  scoping decision, not an omission.
- **Under concurrent requests for the same slot, exactly one succeeds.** The winner
  receives `201 Created`; every loser receives `409 Conflict` carrying the error code
  `SlotAlreadyBooked`. Never a silent overwrite, and never a 5xx.
- Booking a slot that does not exist returns 404. Booking while unauthenticated
  returns 401.

## 5. Viewing a schedule — *assignment #4*

- Any authenticated user can view any room's schedule for a date range inside the
  horizon.
- Each slot is returned with its start, its end, and whether it is booked.
- **Non-admin users see no booker identity** — only free or booked, plus a flag
  marking slots they booked themselves.
- Admins can list all bookings across all users.

## 6. Real-time updates — *assignment #7*

- When a slot's status changes, everyone currently viewing that room's schedule sees
  it **immediately, without refreshing**.
- Updates are scoped to the room: one SignalR group per room, so viewers of room A
  are not woken by activity in room B.
- The broadcast carries **no personal data** — slot identity and new status only,
  consistent with the visibility rule in §5.
- The broadcast happens only **after** the booking write has committed.

## 7. Time — *assignment #4*

- All instants are stored in UTC.
- All times are displayed in a single fixed zone, **Europe/Kyiv**. There is no
  per-user or per-room time zone.
- The zone is a product choice and has nothing to do with the Azure region: the rooms
  are fictional, so the only thing the choice buys is legibility to whoever opens the
  deployed application, and a reviewer reading the grid on their own wall clock is the
  most legible outcome. Rendering in the *viewer's* zone was considered and rejected —
  the grid's defining property is that it runs 08:00–18:00, and that stops being
  visible the moment two viewers in different zones see different hours.
- The API returns UTC instants and names the zone once per schedule response, rather
  than pre-formatting times or storing a zone per row. Clients render with it.

## 8. Authentication — *assignment #3*

- JWT access token only. No refresh tokens: the session lasts roughly 8 hours and the
  user logs in again on expiry.
- The token is the only credential the frontend holds.

## 9. Deployment and submission — *assignment #2, #8, #10*

- Backend and frontend are served by **one** Azure Web App; the frontend is static
  files under `wwwroot`, so there is no CORS and no cross-origin SignalR negotiate.
- The deployed app is reachable at a single public URL, seeded with an admin account
  and demo rooms so a reviewer lands on a populated application.
- The README carries the deployed URL and the repository URL.

## 10. Reviewability — *assignment #6, #9*

- The concurrency guarantee is covered by an **automated test in the repository that
  the reviewer can run**, firing multiple simultaneous requests at one slot and
  asserting that exactly one booking is created.
- The README explains the concurrency mechanism by name, what happens when two
  requests race, and the trade-off accepted.

## Explicitly out of scope

Named so that their absence reads as a decision rather than an oversight:

- Cancelling, rescheduling or editing a booking
- One booking spanning several consecutive slots
- Per-room schedules, custom slot lengths, or closed days
- Recurring bookings
- Email, notifications or calendar integration
- Refresh tokens, password reset, email confirmation, account lockout
- Self-service role management or an admin user-management screen
- Rate limiting
- Multi-tenancy, or rooms belonging to organisations
- Search, filtering or pagination beyond what a list plainly needs
